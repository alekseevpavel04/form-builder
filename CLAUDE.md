# form-builder

Сервис форм отклика. Менеджер собирает форму в `/admin`, публикует её по уникальной ссылке, студент заполняет, менеджер смотрит ответы и воронку заполнения. Вторая задача сервиса: показать, на каком поле студенты бросают форму, и снизить число брошенных форм.

## Запуск и проверка

- `npm install`, затем `npm start` из корня. Сервис на `http://localhost:3000`, порт меняется переменной `PORT`. Админка `/admin` без авторизации.
- `npm test`: тесты на `node:test`, unit и интеграционные через HTTP.
- Node.js 20, 22 и 24 на Windows, macOS и Linux. CI в `.github/workflows/` гоняет ту же матрицу.
- Данные лежат в `data/`. Папка создаётся при первом старте и не коммитится. Если данных нет, сервер создаёт демо-форму.

## Раскладка

- `src/`: сервер. `server.js` точка входа (порт, папка данных, демо-форма), `app.js` маршруты, `http.js` ответы, чтение тела и статика, `store.js` JSON-файлы с атомарной записью, `demo.js` демо-форма. Обработчики по темам: `forms.js` формы и публикация, `responses.js` ответы и CSV, `events.js` приём событий, `analytics.js` воронка и «где уходят».
- `public/`: то, что браузер получает как есть, без сборки, по адресу `/static/`. `shared/schema.js` правила формы и ответов (сервер и браузер), `form/` страница студента (`render.js` рендер, общий с превью конструктора; `session.js` id сессии и черновик в localStorage; `track.js` отправка событий), `admin/` админка (список, конструктор, ответы, аналитика), `lib/` обёртка над `fetch` и создание элементов.
- `tests/`: тесты `*.test.js`; `helpers.js` поднимает приложение на свободном порту с данными во временной папке.
- `data/`: `forms.json`, `responses.json`, `events.json`. Создаётся при старте, путь меняется переменной `DATA_DIR` (нужна тестам).
- `.github/workflows/ci.yml`: `npm test` и запуск на `PORT` под Linux, Windows, macOS на Node 20, 22, 24.
- `docs/screenshots/`: скриншоты для README, сняты на демо-форме. После изменения интерфейса, который на них виден, снимаются заново.

## Инварианты

Это правила, нарушение которых ломает сдачу. Перед изменением, которое их задевает, остановись и обоснуй.

1. Запуск только двумя командами на чистой машине. Никаких нативных аддонов (`better-sqlite3`, `node:sqlite` которого нет в Node 20), шагов сборки, глобальных пакетов, внешних сервисов, CDN и API-ключей. Новая зависимость добавляется, только если без неё код заметно хуже, и проверяется установкой на Node 20.
2. Схема формы единственный источник правил валидации. Сервер проверяет каждую отправку по схеме опубликованной формы, что бы ни прислал клиент: обязательность, тип, формат, варианты из списка, неизвестные поля. Клиент использует те же правила, чтобы показать ошибку у поля до отправки.
3. Запись данных не теряет их при падении процесса и при параллельных запросах: атомарная запись (временный файл и rename) и одна запись за раз.
4. Аналитика собирает только анонимный случайный id сессии, тип события (`view`, `start`, `field_completed`, `submit`), id поля и время. Содержимое полей, нажатия клавиш, IP и user agent не собираются. Любое изменение состава событий меняет строку о сборе данных в README в том же коммите.
5. Всё, что ввёл менеджер или студент (названия, подсказки, варианты, ответы), выводится как текст, а не как HTML. CSV экранирует кавычки и переводы строк и не даёт ячейке начаться с `=`, `+`, `-`, `@`.
6. Снятая с публикации или несуществующая форма показывает понятную страницу, а сервер отклоняет отправку в неё. Это проверяется тестом.
7. Не добавляем то, чего не просили: авторизацию, мультиязычность, перетаскивание полей мышью, аккаунты, уведомления.

## Как проверять изменения

- После каждого изменения `npm test`. Новое поведение получает тест, исправленная ошибка получает тест, который падал до исправления.
- Интеграционные тесты поднимают сервер на свободном порту с данными во временной папке и ходят в него по HTTP. Реальная `data/` в тестах не трогается.
- Изменение интерфейса проверяется в браузере в двух ширинах: 1280 и 390 пикселей. Ошибка должна быть видна у поля, а не только в консоли.
- Готово, когда `npm test` зелёный и сценарий руками пройден: создать форму, опубликовать, заполнить с ошибками и без, увидеть ответ в таблице, выгрузить CSV, увидеть воронку, снять с публикации.

## Код

- Читается без знания фреймворков: простые модули, явные имена, без лишних слоёв.
- Комментарий объясняет, почему так, а не что делает строка.
- Ошибка обрабатывается там, где с ней есть что делать. Неверный ввод даёт ответ 4xx с текстом, а не падение процесса.
- ES-модули, зависимостей нет. Встроенные модули с префиксом `node:`, пути через `path.join` от `import.meta.url`, а не склейкой строк.
- Браузерный код это ES-модули из `public/`. Модуль, который нужен и серверу, и браузеру (правила валидации), лежит в `public/shared/` и не трогает API Node и DOM.
- Неверный ввод в обработчике: `throw new HttpError(4xx, 'текст по-русски')`, ответ из неё делает роутер. Ошибки валидации полей идут в ответе объектом `{ errors: { <id поля>: 'текст' } }`.
- Новый тест это файл `tests/<что>.test.js`. Глобы в `npm test` не добавлять: в Node 20 их нет.
- Тексты интерфейса и сообщения в консоли по-русски. Код, имена и сообщения коммитов по-английски.
- Коммит на одно изменение по смыслу, короткое сообщение в повелительном наклонении.
